# 三腿实盘策略挂单设计

日期：2026-08-27

## 目标

让用户在网站策略确认页一次确认一个策略，并按该策略的三个入场点同时提交三笔 Binance USDⓈ-M 真实限价 Post Only 订单。三笔订单必须分别可追踪；如果任一笔提交失败、超时结果未知或无法确认，系统立即停止后续业务动作并进入需要对账状态。

## 范围

- 只支持网页管理员会话发起的一个 `LIVE_ARMED` 策略，入场腿可为 1–10 笔（默认三笔）。
- 三腿默认使用 `MA + ATR × 倍数`、`MA`、`MA - ATR × 倍数`；横向策略使用同一静态价格但仍生成三笔独立订单。
- 三笔订单在一次最终确认后并发提交。Binance 没有跨订单原子事务，因此接口必须如实展示每一笔的受理结果。
- 订单成交后的退出继续使用现有真实仓位按比例市价 `reduceOnly` 平仓入口。
- PAPER 策略调度器、AI、雷达和后台任务仍不得发送真实订单。

## 不在本次范围

- 不开放提现、转账、划转、修改杠杆或保证金模式。
- 不把 PAPER 策略自动转换为 LIVE。
- 不在部署、测试或启动服务时自动发送真实订单。
- 不把失败的订单自动改成市价单，不因 Post Only 被拒而改变用户设定的价格。

## 订单语义

1. 用户在最终确认页明确选择实盘，页面展示每个点位、数量、预计名义金额、Post Only 和有效期。
   “总投入 USDT”及每腿金额均表示用户实际投入的保证金；服务端读取该合约当前 Binance 杠杆，按“保证金 × 杠杆”计算下单名义价值，用户不需要输入杠杆后名义金额，也不会由系统修改杠杆或保证金模式。
2. 服务端重新读取公开已收盘 K 线、MA/ATR、Binance `exchangeInfo` 数量与价格规则，以及账户可用余额；浏览器传来的数量和价格只能作为展示输入，不能作为最终下单依据。
3. 三笔均通过固定 IP loopback Binance gateway 发送：`LIMIT`、`GTX`、对应方向、精度取整后的价格和数量、唯一 `newClientOrderId`。服务端在提交前读取 `positionRisk` 判断账户是单向还是双向持仓：单向订单显式发送 `positionSide=BOTH`；双向做多发送 `LONG`、做空发送 `SHORT`，不得依赖 Binance 默认值。
4. 在发送第一笔之前完成全部腿校验；任一腿低于 `minQty`、按杠杆换算后的名义价值低于 `minNotional`、数量步长取整后为零或余额不足，则一笔都不发送。
5. 全部请求并发执行。成功回报记录 Binance order ID 和状态；超时先按唯一 client order ID 查询一次，查询不到则记录 `UNKNOWN`，不得重复下单。
6. 任一腿失败或未知时，策略状态为 `RECONCILIATION_REQUIRED`；已受理的订单保持可见，用户必须先查看/撤销/对账，系统不继续提交新订单。
7. 三笔均受理后，策略状态为 `ACTIVE`，页面显示网站订单号、Binance 订单号、价格、数量和状态。

## MA 入场重挂

- MA 入场策略按其周期自动重挂：15m 每两根已收盘 K 线（30 分钟）、1h 每根已收盘 K 线、4h 每根已收盘 K 线。到期时，所有未成交剩余入场单一律先确认撤销，再按最新 MA/ATR 生成新一轮订单，即使交易所精度取整后的价格或数量恰好未变。
- 读取 K 线、账户、规则或订单状态在撤单前暂时失败时，策略保持 `ACTIVE`，记录脱敏错误并由每分钟调度器重试；不把短暂读取故障误标为订单异常。
- 只要已开始撤单或提交新单，任何不确定回执、缺少成交明细或本地与交易所状态不一致都必须进入 `RECONCILIATION_REQUIRED`，不得自动补单。

## 安全边界

- 所有变更 API 要求管理员会话、同源请求、服务端实盘开关和 `BINANCE_GATEWAY_TRADING=true`。
- 页面最终确认使用固定确认短语；本次确认不会自动触发第二次请求或重放。
- API key、secret、gateway token、会话 token 和完整 Binance 响应不得进入浏览器、数据库或日志。
- 每个订单使用独立 client ID，订单超时只查询不重试。
- 入场与保护订单必须与 Binance 当前持仓模式匹配；双向保护单发送对应 `positionSide` 且省略 `reduceOnly`，单向保护单发送 `reduceOnly=true`。
- VPS 仍只允许 Caddy 对外，网站和网关仅监听 loopback。

## 验收

- 三腿策略请求一次确认后会生成三个稳定网站订单号并并发提交三个真实订单请求。
- 三腿任一预校验失败时，fake gateway 的请求数为零。
- 三腿部分成功时不会提交第四笔或重试已提交腿，状态为 `RECONCILIATION_REQUIRED`，并保留每腿结果。
- 请求超时且 client ID 查询不到时标记 `UNKNOWN`，不会重复下单。
- 页面显示三笔订单及异常原因；刷新后仍能从服务端读取策略状态。
- 所有自动化测试只使用 fake gateway；部署和启动不发送真实订单。
