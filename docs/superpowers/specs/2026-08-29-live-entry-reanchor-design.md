# 实盘均线跟随入场、止损撤单与成交生命周期设计

日期：2026-08-29

## 目标

将 `web` 与 `tele` 发起的 MA 实盘入场策略从“一次性固定价格挂单”升级为“目标仓位持续补齐”的策略组。

每个策略组以最新**已收盘** K 线的 MA30 和 ATR14 为锚，按配置的 ATR 偏移计算限价 Post Only 入场单。未成交数量会按周期规则撤旧重挂；已成交数量不重复入场，并从第一笔成交起受同周期动态止损保护。策略组所有已成交数量完全止盈或止损退出后，在图表上以真实成交的数量加权成交均价绘制入场到出场的虚线。

同时建立全账户订单归档与复盘模块：归档每一个可获得的 Binance 订单编号和成交，识别订单来源、入场/出场方式、策略周期、风险参数、持仓时长与真实盈亏。复盘统计只在归属可信时形成完整交易周期；无法可靠配对的 Binance 原生手动订单仍完整展示原始成交与已实现盈亏，但绝不被错误合并到另一笔策略中。

## 已确认规则

- 金额输入仍表示总保证金；目标名义金额 = 总保证金 × 创建/刷新时读取到的 Binance 当前杠杆。
- MA 策略的入场价格为每条腿 `MA30 + ATR × atrOffset`。多头提交 `BUY`、空头提交 `SELL`，两边使用同一价格计算规则。
- 只使用已收盘 K 线。未收盘 K 线不会触发撤单、重挂或止损判断。
- MA 类型、MA 长度、ATR 长度和 ATR 倍数是策略创建时锁定的参数；每次入场刷新和止损检查都用该参数重新计算**最新已收盘 K 线**的 MA/ATR 数值。因此入场锚点与止损边界都会随 K 线移动，不能冻结为创建时的价格。
- 某条腿部分成交后，已成交部分进入来源绑定的自动保护；该腿尚未成交的剩余数量以及其他未成交腿，仍可在下一次到期刷新时随均线移动。
- 每轮刷新只为“策略目标数量减去累计实际成交数量”的差额挂单，禁止重复补入已成交数量。
- 任一已成交来源触发动态止损时，立即冻结整个策略组的入场刷新，撤销该组所有尚未成交的入场挂单；不得再按均线补仓或创建新入场单。
- 成交均价采用数量加权成交均价（VWAP），不使用价格中位数。

## 周期与刷新节奏

当前挂单所依据的已收盘 K 线称为“锚定 K 线”，并计为第 1 根。策略调度器每分钟运行，但仅在策略实际到期时读取行情与交易所状态。

| 周期 | 未成交入场单刷新条件 |
| --- | --- |
| `15m` | 锚定 K 线加上两根后续已收盘 K 线，即第 3 根收盘时刷新 |
| `1h` | 锚定 K 线加上两根后续已收盘 K 线，即第 3 根收盘时刷新 |
| `4h` | 每根后续已收盘 K 线刷新 |
| `1d` | 每根后续已收盘 K 线刷新 |

自动均线跟随仅适用于以上四个周期的 MA 策略。横向价位策略保持固定价；其他自定义周期在没有明确刷新规则前保持固定价，并在界面中明确显示“未启用自动跟随”。

## 策略组状态与数据模型

现有 `live_strategy_orders` 对同一“策略 / 腿 / intent”有唯一约束，不能安全保存同一腿多轮撤单重挂。因此新增不可变的订单尝试账本，保留原始订单与未来代次的完整历史。

### 新增记录

- `live_strategy_generations`
  - 策略组号、代次、锚定已收盘 K 线 ID、MA、ATR、计划刷新时间、刷新原因、状态和处理锁。
- `live_strategy_order_attempts`
  - 代次、策略腿、稳定 clientOrderId、Binance orderId、方向、价格、原始数量、累计成交数量、成交均价、状态、撤单结果与错误。
- `live_strategy_execution_fills`
  - 策略组、来源订单、角色（`ENTRY` / `EXIT`）、Binance 成交 ID、数量、真实成交价格和成交时间。
- `live_strategy_lifecycle`
  - 策略组的累计入场/出场数量、数量加权入场均价、数量加权出场均价、首次入场时间、最后出场时间、关闭原因和图表生命周期状态。

现有策略和订单在首次迁移时作为第 1 代账本记录导入，不改变既有 Binance clientOrderId，也不重新下单。

## 未成交差额的撤旧重挂流程

1. 调度器先根据策略的锚定 K 线和周期判断是否到期；未到期时不请求该策略的行情或 Binance 订单。
2. 到期时获得策略组锁，并逐笔按 clientOrderId 向 Binance 对账。超时只查询一次；任何未知状态、数量不一致或锁竞争都进入 `RECONCILIATION_REQUIRED`，不创建新单。
3. 将每笔实际成交同步到来源保护与成交账本。策略的“待补齐差额”仅由累计成交数量计算。
4. 若待补齐差额为零，策略标记“目标已全部成交”，停止入场刷新，继续按策略周期执行动态止损和止盈管理。
5. 对所有仍有未成交数量的入场尝试发送显式撤单。只有全部撤单获得确定结果后，才读取最新已收盘 K 线、交易所精度、当前杠杆和余额。
6. 以新 MA30/ATR、每腿目标保证金和累计成交结果生成下一代 1–10 笔 `LIMIT + GTX` 挂单；新一代使用新的 `teleIN...` / `webIN...` clientOrderId。
7. 价格和数量经 Binance tick/step 精度取整后若与仍有效订单完全一致，则仅记录“已检查”并推进锚定 K 线，不产生撤单或新单。
8. 任一撤单或新单失败、被拒绝或结果未知时，策略停止自动刷新并提示对账；系统不以市价补单、不盲目重试、不修改杠杆或保证金模式。

当服务重启、定时器延迟或漏过多个周期时，只基于最新可用的已收盘 K 线执行一次对账与刷新，并把该 K 线设为新的锚定；不得连续补跑多轮撤单/下单。

## 动态止损与止损后的撤单

从策略组第一笔入场成交起，按该策略自身的周期、MA 类型/长度、ATR 长度与 ATR 倍数监听每根新已收盘 K 线。无论策略是 `15m`、`1h`、`4h` 还是 `1d`，都在该周期每根新收盘 K 线到来时重新计算边界，而不是使用创建策略时的固定止损价格：

- 多头：收盘价跌破 `MA - ATR × 倍数` 为失效；
- 空头：收盘价突破 `MA + ATR × 倍数` 为失效；
- 第一次连续失效：对该策略组已成交且可安全归属的来源数量执行 50% 保护性市价退出；
- 第二次连续失效：退出剩余数量；价格回到安全侧后，连续失效计数归零。

首次失效被确认时，策略组立即写入不可逆的 `ENTRY_FROZEN_BY_STOP` 状态并撤销所有未成交入场单。即使撤单出现异常，策略也不得继续刷新或加仓；已成交来源仍按来源数量隔离执行/继续执行保护，数量无法对账时转为待对账，绝不动用其他来源仓位。

## 图表成交生命周期线

同一 `TW-L-S-*` 策略组跨所有代次汇总真实 Binance 成交：

- 入场端点：所有 `ENTRY` 成交的数量加权成交均价，时间为首次入场成交时间；
- 出场端点：所有 `EXIT` 成交的数量加权成交均价，时间为最后一次出场成交时间；
- 仅当该策略组的全部实际入场数量都已退出后绘制；未成交目标数量不会阻止在止损撤单后关闭已成交部分；
- 两点之间绘制虚线：总已实现盈亏大于等于零为绿色，否则为红色；
- 保留现有成交点颜色：买入绿色、卖出红色、平仓黄色；图例显示策略组号、入场/出场均价、实际成交数量、已实现盈亏和收益率。

图表不从当前合并持仓反推历史。它只使用策略组绑定的真实成交账本，避免将 iOS、Alex、其他 Web 或 Telegram 订单混入该策略的盈亏线。

## 全账户订单归档与复盘模块

### 覆盖范围与来源识别

归档目标是 Binance USDⓈ-M 账户中每个可获得的订单编号、订单更新和真实成交，而非只保存 Workbench 创建的订单。每笔归档记录保留 Binance `orderId`、原始 `clientOrderId`、symbol、方向、持仓方向、订单类型、Post Only / reduce-only 属性、价格、数量、成交明细、手续费、已实现盈亏和时间。

来源只按可验证证据标记，绝不改写 Binance 原始 clientOrderId：

- `tele...`：Telegram 策略或其策略保护单；
- `web...`：Workbench 网站策略或其策略保护单；
- `alex...`：Workbench 网站手动下单、手动平仓或手动保护单；
- 其余原始 clientOrderId：`BINANCE_NATIVE`，即 Binance 网页、iPhone、iPad 或其他 Binance 原生端手动订单；
- 无 clientOrderId 或历史字段缺失：保留为 `UNCLASSIFIED`，不猜测来源。

对 `web` / `tele` 策略，`TW-L-S-*` 是精确的策略组号；对 Alex 和 Binance 原生订单，只有在同一笔订单或交易所返回的已实现盈亏可直接证明归属时才标记为精确。单向持仓中多个同币种手动订单可能在 Binance 侧合并，系统不得假装能精确配对：此类记录显示为“已实现盈亏可见、入出场配对未归因”，并允许后续人工建立复盘分组。

### 数据采集与一致性

1. 新增只读订单归档服务。首选 Binance 用户数据流接收未来所有 `ORDER_TRADE_UPDATE`，确保任意币种的原生手动订单也能进入归档。
2. 归档服务同时按固定频率做签名只读对账：活跃持仓、开放订单、已知策略币种和最近更新的币种通过 `allOrders`、`userTrades` 与收入记录校正遗漏或连接中断。
3. 初次历史导入使用 Binance Futures 官方订单/成交历史下载接口分批执行，保存同步水位；限速、分页和重试均在服务端队列中完成，不在浏览器批量请求交易所。
4. 所有原始订单与成交以 Binance `orderId` / trade ID 去重并不可变存储；后续分类、策略关联和人工复盘标签为单独的可审计层，不能覆盖原始证据。
5. 用户数据流断开、历史导入失败或某个币种无法读取时，归档状态显示缺口时间段和原因；统计默认排除不完整区间，避免把缺失数据当作亏损或盈利。

### 复盘数据模型

- `trade_order_archive`：原始订单快照与最新状态；
- `trade_fill_archive`：每一条 Binance 成交、手续费、已实现盈亏和归属置信度；
- `trade_review_groups`：策略组、可精确配对的手动交易，或用户创建的原生订单复盘组；
- `trade_review_metrics`：入场/出场 VWAP、净盈亏、毛盈亏、手续费、资金费、持仓时长、最大有利/不利波动、关闭原因和统计版本；
- `trade_review_tags`：可检索的入场周期、来源、入场/出场方式、策略参数、方向、时间段、市场环境和用户备注。

每个完整复盘组至少记录：币种、方向、策略周期（没有可靠记录时显示“未记录”）、首次入场与最终出场时间、持仓时长、入场/出场 VWAP、总保证金、实际杠杆、最大名义价值、分批次数、均线重挂代次、部分成交次数、止损/止盈/手动平仓原因、入场和出场分别来自手动或策略、订单类型（市价 / 限价 / 条件 / Post Only）、手续费、资金费、已实现净盈亏及归属置信度。

### 统计与分析界面

新增“交易复盘 / 统计”页面，支持按日期、币种、来源、方向、策略周期、入场方式、出场方式和归属置信度筛选。默认只展示完整且精确归属的交易，并允许用户切换查看未归因原始订单。

核心统计包括：

- 净盈亏最高和最低的策略组 / 手动订单，以及对应币种、周期、持仓时长、入出场方式和退出策略；
- 胜率、平均盈利、平均亏损、盈亏比、期望值、Profit Factor、总手续费与资金费；
- 按周期、币种、方向、来源、入场方式、退出原因、持仓时长、入场 ATR 距离、重挂次数和时间段分组的结果；
- 盈利交易的平均与分位数空间、亏损交易的常见止损原因和最大不利波动；
- 时间序列净值/已实现盈亏曲线，以及可点击进入原始订单、成交、图表生命周期线和策略事件的回放。

统计页面只陈述数据与可复现的分组结果；对“亏损常见原因”等结论必须同时展示样本数、过滤条件和原始订单链接，样本不足时显示“样本不足”，不生成确定性结论。

### 复盘模块验收

1. Workbench、Telegram、Alex 与 Binance 原生订单均按原始 clientOrderId / 可验证来源归档，且不修改交易所原始编号。
2. 策略组跨多轮均线重挂后，所有入场、撤单、成交、止损和止盈仍归于同一 `TW-L-S-*` 复盘组。
3. Binance 原生的重叠手动仓位不会被错误自动配对；不确定性必须显式展示。
4. 每个精确关闭的复盘组均能显示 VWAP、净盈亏、费用、持仓时长、入场/出场方式、周期与退出原因。
5. 排行、分组、收益空间和亏损原因统计可回链到原始订单/成交，且缺失数据不会进入默认统计。

## 用户界面与 Telegram 状态

网站和 Telegram 的策略状态必须显示：

- 策略组号、周期、目标保证金、当前杠杆换算后的目标名义金额；
- 已成交名义金额 / 待补齐名义金额、累计成交数量与平均入场价；
- 当前代次、锚定 K 线、最新 MA/ATR、下一次预计刷新时间；
- 每个历史订单的创建、成交、撤销、替换或待对账状态；
- `目标已全部成交`、`止损冻结并撤余单`、`已完整退出` 等明确状态；
- 发生撤旧重挂、目标全部成交、止损冻结、撤单异常、保护异常与策略关闭时的 Telegram/Bark 通知。

## 安全与风控边界

- 只有用户已明确确认创建的 `web` / `tele` 实盘策略可自动撤旧重挂；手动 iOS、Alex 订单完全不参与。
- 所有入场单仍是 `LIMIT + GTX`；Post Only 被拒绝不转市价单。
- 每次实际下单、撤单和止损前均使用固定 IP loopback 网关、服务端实盘双开关、唯一 clientOrderId 和一次性超时查询。
- 以策略组锁、每根 K 线幂等键和不可变订单尝试账本防止 timer 重叠、重启或网络超时导致重复撤单/下单。
- 行情读取按“到期策略”聚合，并复用相同 `symbol + timeframe + MA/ATR` 快照，避免分钟调度造成无意义的 Binance 请求。
- 测试、构建、部署和服务重启必须使用 fake gateway 或只读调用，禁止创建真实订单。

## 验收标准

1. 多空各验证 `15m`、`1h`、`4h`、`1d` 的刷新计数与最新已收盘 K 线锚定，其他周期不自动刷新。
2. 部分成交后，刷新仅替换未成交差额；累计已成交数量不会重复入场。
3. 任一已成交来源首次触发止损时，剩余入场单被撤销且策略从此不再产生新入场单。
4. 撤单、下单或查单出现未知结果时，策略进入待对账，绝不继续补仓或重复提交。
5. 服务重启、同一根 K 线重复调度、漏过多个周期均不会产生重复撤单或多轮补单。
6. 全部实际成交退出后，图表生命周期线使用数量加权真实成交均价，且不混入其他来源订单。
7. 既有策略、保护账本、手动订单保护、双向持仓模式和 Binance 精度/最小名义金额校验保持兼容。
