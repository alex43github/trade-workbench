# Telegram 可靠响应与分区自选币扫描设计

## 目标

在不增加真实交易权限、不触发 Binance 风控的前提下，恢复 Telegram webhook 的可诊断可靠性，并将自选币实现为按来源分区、稳定排序的服务端投影。北京时间 08:05 进入连续扫描周期，每小时以已收盘 1h K 线更新机器自选；每 4 小时同一轮附加 4h 确认，仅影响机器候选排序。

## 边界与非目标

- 不打开 `BINANCE_GATEWAY_TRADING`、`BYBIT_GATEWAY_TRADING` 或任何应用实盘开关；不创建、取消或修改交易所订单。
- 不在浏览器保存 Telegram、Binance、Bybit 或维护令牌；日志只写脱敏状态码和稳定错误分类。
- 不把 4h 形态作为机器入选的替代条件。机器入选和移除只使用已收盘 1h 的 MA30、ATR14、阈值 1 ATR、连续根数 3。
- 不替换既有雷达/反转策略；只复用其 4h 已完成结果作为排序确认信号。

## Telegram webhook

webhook 仍是唯一入口，依次执行：路径与 secret 校验、更新解析、授权私聊校验、更新幂等 claim、会话处理、callback 确认和消息回发。每个边界产生一条不含消息正文、token、callback 原始内容或订单资料的诊断事件，包含 `stage`、`updateId`、`outcome`、安全错误码和时间。

鉴权、解析和未授权用户继续返回 401/400；已经处理或已 claim 的重复更新返回 200。处理器或 Telegram 回发失败返回 500，并只在失败前未成功发送响应时允许 Telegram 重试。实现必须避免把“已 claim 但回发失败”永久吞掉：claim 存储须有可重试的处理状态，或在发送失败时释放该 update 的 claim。选择现有存储能力所支持的最小方案，并用测试锁定其幂等性。

## 自选来源和视觉投影

现有来源表是唯一事实来源。每个 symbol 可拥有以下任意集合：`PINNED`、`POSITION_BINANCE`、`POSITION_BYBIT`、`MANUAL`、`ATR_STRONG_1H`。为避免破坏已有 `POSITION` 数据，迁移必须把它映射为 Binance 持仓来源；API 对外仍可聚合为“持仓”分区。

服务端返回 `WatchlistSection[]`，每段含稳定 id、标题、items；扁平数组可保留作为兼容字段。分组与顺序固定：

1. 主流：BTC、ETH、SOL、HYPE、ENA，顺序恒定。
2. 持仓：任一交易所非零仓位，按照首次进入该分区时间、symbol 排序；两个交易所同币只显示一次。
3. 手动：仅用户添加的 `MANUAL` 来源，按加入时间、symbol 排序。
4. 机器自选：仅 `ATR_STRONG_1H` 来源，强度降序、symbol 升序。

同一个币仅显示于最高优先级分区。四段之间渲染实线分隔符；空段不渲染分隔符或标题。移除星标只撤销 `MANUAL`，机器扫描和持仓同步只能写各自来源。

## 机器强度与生命周期

使用最后一个已收盘 1h bar 计算 `MA30` 与 `ATR14`。多头要求 `close > MA30 + ATR`；空头要求 `close < MA30 - ATR`。最新同侧连续根数少于 3 不入池；入池后，最新已收盘 bar 回到或穿过阈值立即移除 `ATR_STRONG_1H`。数据不完整、超时、限流或扫描降级时不得自动移除原有机器来源。

强度是只读、可重算的排序字段：首先连续阈值外根数降序，其次最新有利 ATR 距离（多头 `(close-MA30)/ATR`，空头 `(MA30-close)/ATR`）降序，然后 4h 已确认形态布尔值降序，最后 symbol 升序。2ATR、3ATR 因而自然排在前面；4h 确认只在 4 小时轮次更新，缺失时为未确认而非失败。

## 调度、速率与失败处理

维护 timer 保持每小时 `:05` 触发，但调度器在北京时间 08:05 开始此周期，并持续覆盖午夜后的 00:05、04:05。每一轮执行 1h 机器扫描；北京时间小时为 0、4、8、12、16、20 时同一请求额外运行 4h 确认。08:05 继续运行既有 daily 任务。

扫描器只使用 Binance 公共 K 线接口；一币一次 1h 请求后，4h 轮次再读取一次 4h K 线。采用有限并发（默认 1）、每请求最小间隔（默认至少 300ms）、对 429/5xx 指数退避一次并记录降级；不赶时间，不进行无上限并行重试。持仓同步沿用既有只读 Binance/Bybit 账户接口，任一读取失败时保留该交易所旧来源。

## 验收

- webhook 测试覆盖每个安全边界、回发失败可重试、重复更新不重复发消息，并且所有日志字段均不含机密或用户消息正文。
- 自选测试覆盖四段排序、跨来源去重、两交易所持仓、手动/机器独立撤销和空段 UI 分隔符。
- 纯函数测试覆盖 1ATR 三根入池、回落删除、2/3ATR 强度排序、降级保留和 4h 确认仅影响排序。
- 维护调度测试覆盖 08:05、12:05、00:05 与非 :05；所有扫描网络测试使用 fake fetcher，断言未请求任何私有或订单端点。
- 本地集成后运行 focused tests、类型检查、构建和 `git diff --check`；部署前/后核验所有交易开关仍为关闭。
