# Telegram 私聊交易机器人与实盘条件执行设计

日期：2026-08-26

## 目标

在既有 Trade Workbench 上增加一个仅供单一管理员 Telegram 私聊使用的交易机器人。机器人与网页使用同一套策略、网站订单编号、审计和 Bark 通知；用户在无法打开网页时，可通过递进对话创建、查看和取消策略。

机器人支持 `PAPER` 和 `LIVE_ARMED` 两种模式。实盘策略只能由白名单用户在 Telegram 最终摘要页主动确认后创建；AI、雷达、后台任务和机器人自身均不得自行创建、武装、修改或取消实盘策略。部署、测试和实现阶段不得发送真实 Binance 订单。

## 已确认的交易语义

- 合约：仅 Binance USDⓈ-M `USDT` 永续合约。
- 杠杆：读取账户在该合约已配置的默认杠杆；不得调用任何修改杠杆或保证金模式接口。
- 入场：默认三笔等额、限价 `GTX`（Post Only）订单，围绕指定 `SMA` 或 `EMA` 的 `MA ± ATR × 倍数` 布局；用户可选择 1 至 10 笔。
- 入场腿：只在新已收盘 K 线上重算完全未成交的均线腿；部分成交腿保留原价和剩余数量。策略默认有效期 7 天，到期仅撤销未成交入场腿。
- 动态止损：按指定周期的已收盘 K 线确认。多头收盘跌破 `MA - ATR × 倍数`、空头收盘突破 `MA + ATR × 倍数` 时，第一根触发 `reduceOnly` 市价止损，默认退出已成交策略仓位的 50%；下一根仍失效时市价退出其余仓位。横向关键位可作为附加失效条件。
- 止盈：每个实际成交批次独立计算毛利润；达到该批次实际成交金额的 100% 时，使用限价 Post Only 退出初始数量的 25%；达到 200% 时退出初始数量的 40%；余下 35% 跟随动态/横向守卫。不得把止盈自动转换成市价单。
- 取消：取消策略会撤销该策略尚未成交的入场和未成交限价止盈单；不会在未获得新的用户确认时平掉已经持有的实盘仓位。

## 安全边界

### Telegram 身份

- 只处理私聊更新，且 `from.id` 与 `TELEGRAM_ALLOWED_USER_ID` 完全一致。
- 拒绝群聊、频道、未知用户、无效或过期回调、重复 `update_id` 和乱序/过期会话操作。
- 不用 Telegram username、chat title 或转发来源作为身份依据。
- 机器人令牌、Webhook 隐藏路径和 Webhook secret 只保存在 root-owned、0600 的 `/etc/trade-workbench/workbench.env`；不得存数据库、浏览器、日志、Bark 或 Telegram 文本。

### Webhook

- Caddy 是唯一对公网监听的进程；网站接收 `POST /api/telegram/webhook/<opaque-path>`，不新增端口。
- 同时校验不可预测的路径和 `X-Telegram-Bot-Api-Secret-Token`，以常量时间比较 secret。
- Webhook 响应快速返回；回复消息、编辑摘要与 Binance 操作由服务端受控任务处理。
- 每个 Telegram `update_id` 只处理一次；回调数据只承载短的不透明动作 ID，所有金额、币种和策略参数只从服务端会话读取。

### Binance 与实盘门禁

- 只有 root-owned 环境变量将 `BINANCE_GATEWAY_TRADING=true` 时，受限网关才允许实盘变更请求；默认和测试环境均为 `false`。
- Binance API key 仅启用 USDⓈ-M Futures 所需权限，关闭提现、转账和资产划转，并仅白名单 VPS 出口 IPv4 `139.59.99.126`。
- 网关仅监听 `127.0.0.1:8788`。它只允许本设计列出的账户查询、订单查询、精确下单和精确撤销路径；转账、提现、杠杆修改、保证金模式修改和未列出的写操作永久拒绝。
- 每次实盘最终确认前都重新读取 `exchangeInfo`、账户可用余额、合约默认杠杆、精度过滤器与最小名义金额。失败时不创建订单，并向 Telegram 返回不含密钥/签名的原因。
- 每个 Binance 请求使用稳定的 `newClientOrderId` 或 `clientAlgoId`。网络超时重试前先按该 ID 查询，禁止重复订单。

## Telegram 交互

机器人首页提供持久底部菜单：`默认下单`、`完整策略`、`持仓`、`挂单`、`手动持仓保护`、`策略管理`和`取消/主菜单`。底部菜单使用普通私聊文本触发，参数选择和最终确认继续使用 inline keyboard。

### 快捷默认下单

`默认下单`用于在不重复填写策略参数的情况下创建一组实盘均线入场策略。用户依次输入或选择币种、方向（做多/做空）、周期（15分钟/1小时/4小时/日线）和总保证金（30/50/70/其他）。默认参数固定为 SMA30、ATR14、ATR 倍数 1、5 笔等额 Post Only 限价入场单和既有默认止盈/动态止损规则。

用户输入的金额始终是总保证金，不是名义金额。例如总保证金为 100 USDT、Binance 当前合约默认杠杆为 20 倍时，目标总名义金额为 2,000 USDT，五笔入场单各按 20 USDT 保证金计算数量。点击最终确认时重新读取杠杆、行情、余额和交易所过滤器；默认下单不得绕过一次性确认 nonce、实盘开关、幂等和对账保护。

### 建立策略向导

1. 选择 `模拟盘` 或 `实盘`。
2. 输入或选择 `BTCUSDT` 一类的 USDT 永续合约；服务端验证交易所可交易状态。
3. 选择 `做多` 或 `做空`。
4. 选择周期：`5m`、`15m`、`1h`、`4h`、`1d`、`1w`，默认 `1h`；另提供 `其他`，仅在选择后输入 Binance 支持的自定义周期。
5. 选择 `均线` 或 `关键位`；均线策略使用按钮依次选择 SMA/EMA、长度（30/60/90/200/其他）、ATR 长度（默认14）和 ATR 倍数（0.5/1/1.5/2/2.5/5），关键位策略输入固定入场价与可选横向守卫。
6. 输入总保证金（USDT），再用按钮选择下单笔数（1/2/3/4/6/8/10，默认3）。均线入场腿按 MA ± ATR×倍数区间等距生成：1笔为 MA，3笔为下限/MA/上限，其余笔数包含区间端点并等距排列。系统读取合约当前默认杠杆，并显示每腿保证金、预估名义金额和交易所最小值校验结果。
7. 选择第一根失效 K 线的止损比例，默认 50%；摘要同时明确第二根连续失效时退出剩余仓位。
8. 选择是否使用默认分段止盈；默认启用 100% 毛利润 25%、200% 毛利润 40%、余下 35% 跟随守卫。
9. 展示不可省略的最终摘要：模式、合约、方向、默认杠杆、周期、策略参数、每条腿价格/数量、止损、止盈、7 天有效期和风险提示。
10. 只有摘要页的最终按钮才会创建策略：`确认建立 PAPER 策略` 或 `确认建立实盘策略`。确认按钮只可使用一次；重复 Telegram 回调返回原始结果，不新增订单。

文字输入仅用于金额、周期参数或价格；每次输入均有明确上下文、数值范围和服务端 schema 校验。其他选项使用 inline keyboard。用户可在任意未确认步骤取消，取消不会留下策略或订单。

### 只读查询与管理

- `持仓`：PAPER 显示本地模拟持仓；实盘通过内网网关读取持仓，显示合约、方向、数量、均价、标记价、未实现盈亏、收益率、默认杠杆和强平价。
- `挂单`：PAPER 显示本地策略腿；实盘读取 Binance 当前未成交订单，并关联可识别的网站策略/订单号，显示价格、数量、方向、Post Only/Reduce Only 和状态。
- `策略管理`：显示活跃/等待/部分成交/到期策略和到期时间；用户可选择取消某一策略。取消摘要会明确说明只撤本策略未成交订单、不自动平仓。

## 数据与状态机

新增 Telegram 更新去重表、短期对话会话表和 Telegram 审计事件表。会话含授权用户 ID、步骤、受 schema 校验的草稿、版本、过期时间和一次性确认 nonce；不保存 Bot token、Webhook secret、Binance key 或签名。

现有 PAPER 策略账本保持兼容。实盘使用独立但同构的策略、腿、成交批次、交易所订单映射、守卫检查点和事件表，状态为：

`DRAFT -> WAITING -> ACTIVE -> CLOSED | CANCELED | EXPIRED`

实盘策略的每条腿与每个退出订单均保存：网站订单号、Binance client order ID、Binance order ID、创建来源 `TELEGRAM`、参数快照、状态、修订版本和无敏感信息的审计摘要。Telegram 与网页创建的策略可相互查看和管理。

## 服务端组件

### Telegram client 与 webhook route

Telegram client 封装 `sendMessage`、`editMessageText`、`answerCallbackQuery` 和 Webhook 注册；不依赖第三方消息框架。API route 负责认证、更新去重、会话推进和触发受控动作。消息发送失败不会回滚已经完成的数据库或 Binance 状态，并记录可见但脱敏的诊断。

### Live strategy executor

新增受 systemd 管理的 loopback-only 实盘执行器，读取本地持久化账本和受限 Binance 网关：

1. 在每根相关已收盘 K 线计算策略的 MA/ATR 以及横向守卫。
2. 只刷新完全未成交的入场限价腿；部分成交腿不可移动。
3. 对确认的动态失效执行精确数量的 `reduceOnly` 市价退出；对止盈保持 `GTX` 限价方式。
4. 对订单与成交批次持续对账；服务器重启后以 client order ID 和闭合 K 线检查点恢复，避免重复下单或重复止损。
5. 写入策略、订单、成交和通知事件后，异步触发 Bark 与 Telegram 状态消息。通知失败永不阻塞交易状态持久化。

### Binance gateway

网关新增最小允许列表：USDT 永续账户/持仓/默认杠杆配置查询、当前未成交单查询、通过项目 client ID 查询单、创建限价/止盈/止损订单和按项目订单 ID 撤销订单。每条请求都校验允许的 symbol、数量、`reduceOnly` 语义和所需权限。网关不接受来自浏览器或 Telegram 的直接访问。

## 错误处理

- 未配置机器人、白名单或 Telegram Webhook：机器人功能显示未配置，Web 端健康状态可见；不降级为不受保护的轮询。
- `BINANCE_GATEWAY_TRADING=false`：实盘确认被拒绝，且明确提示没有创建任何订单。
- 余额、精度、最小名义金额、默认杠杆或币种校验失败：保留草稿，提示用户修正；不创建部分订单。
- 首批多腿下单中途失败：用稳定 client order ID 查询已接受订单，停止继续创建新腿，进入 `RECONCILIATION_REQUIRED` 并同时发 Telegram/Bark，绝不推测全成或全撤。
- Telegram 或 Binance 网络失败：使用幂等键安全重试；不能确认结果时保持可见的待对账状态。
- 止盈的 Post Only 限价未成交：保持挂单并通知；系统不得自行变成市价。止损的已收盘 K 线触发执行保护性市价单。

## VPS 上线与配置

可信 HTTPS 域名是 Telegram Webhook 与远程网页登录的前提。部署时：

1. 域名 A 记录指向 VPS，Caddy 成功签发证书。
2. 创建 BotFather bot，设置 token；不把 token 发送给助手、网页或聊天记录。
3. 配置 `/etc/trade-workbench/workbench.env` 的 Telegram secret、唯一用户 ID、Binance read-only 凭据和实盘开关。
4. 先部署并测试 PAPER Bot、持仓/挂单只读查询和 Bark；再显式开启 `BINANCE_GATEWAY_TRADING=true`。
5. 用户在当次操作中明确输入 `CONFIRM` 后，才用最小金额在 Binance 真实环境执行第一笔验收策略。任何由本助手实际提交的生产交易都需要这一当次确认。

## 验收

- Webhook：拒绝无 secret、错误 secret、未知用户、群聊、重复 update、过期 callback 和篡改 callback。
- 对话：覆盖 PAPER/实盘完整向导、所有数值校验、取消、超时恢复、最终确认幂等和默认止盈/止损摘要。
- 查询：模拟与假 Binance 网关验证持仓、挂单、策略状态和网站订单号映射。
- 网关：默认拒绝交易；开启时只允许明确的 Futures 路径；拒绝提现、转账、杠杆和保证金模式修改。
- 实盘执行器：Fake Binance 验证 GTX 入场/止盈、已收盘 K 线的 50% 与剩余仓位市价止损、对账、重启恢复、到期撤单和无重复 client order ID。
- 端到端模拟：Telegram Update -> 对话摘要 -> 最终确认 -> 策略记录 -> Fake Binance 订单 -> Telegram/Bark 通知。
- VPS：HTTPS、Caddy、UFW、loopback 边界、systemd 自动恢复、Webhook 注册、只读查询和 PAPER 后台执行均可验证。

## 非目标

- 不允许 AI、雷达、分析结果或后台任务自主创建/确认/取消实盘交易。
- 不提供提现、转账、资金划转、修改杠杆或保证金模式。
- 不支持群聊、多用户、共享策略或复制交易。
- 不将 Telegram 作为绕过最终确认、VPS 身份边界或 Binance 精度检查的通道。
