# 实盘总开关设计

## 背景

交易页目前同时展示“实盘状态”“系统止损保护”和“实盘开关”三个概念，且前端本地状态可能与服务端真实下单条件不一致。需要收敛为一个由服务端裁决的实盘总开关，避免界面显示为开启但实际不能下单，或用户误以为关闭后既有保护也被取消。

## 目标

- 交易页顶部只保留一个可点击的“实盘总开关”。
- 绿色表示所有必要条件满足且允许新的实盘操作；红色表示实盘功能未就绪或已关闭，并明确原因。
- 开关状态由服务端持久化并裁决，浏览器只展示状态、发起意图，不保存密钥，也不直接决定能否下单。
- 关闭总开关后，禁止新的实盘入场和新的非保护性实盘操作；已经启动的实盘策略、止盈止损、系统保护和对账流程继续运行，除非它们因自身风控或执行错误停止。
- 开启总开关只负责解除“总开关”这一层限制，不绕过账户、网关、环境变量、策略确认和二次确认等既有安全门槛。

## 非目标

- 不在本次改动中自动连接交易所账户或读取浏览器端 API 密钥。
- 不把环境变量开关替换成网页开关；生产环境仍须由部署侧显式允许实盘。
- 不改变现有最终确认、订单签名、止损、对账和权限校验流程。

## 状态模型

服务端同时计算“用户总开关”和“有效实盘状态”。有效状态只有在以下条件全部满足时才为 `live`：

1. 当前操作者通过身份与变更权限校验；
2. 可交易账户已连接；
3. 网关已配置；
4. `BINANCE_GATEWAY_TRADING=true`；
5. `WORKBENCH_LIVE_TRADING_ENABLED=true`；
6. 持久化的实盘总开关为开启。

任一条件不满足都返回 `off`，并返回可供界面展示的原因。服务端不能仅因浏览器点击就返回可下单状态。

## 接口

- `GET /api/trade/live-status`：返回持久化开关、有效状态、原因码和展示文案。继续使用现有操作者认证。
- `POST /api/trade/live-status`：请求体为 `{ "enabled": boolean }`，要求操作者变更权限；服务端重新计算全部门槛后持久化意图并返回最新有效状态。开启失败时不得伪装成成功开启。
- 任何真实下单、撤单、策略启动和保护动作仍必须在服务端再次调用同一有效状态判断，不能信任前端传入的布尔值。

持久化沿用项目现有设置存储，并写入开关变更审计事件（操作者、前后值、原因、时间）。

## 页面行为

- 删除顶部并列的“系统止损保护”和旧式“实盘开关：开启/关闭”表达，改为一个同时承担状态展示和开关操作的控件。
- 控件使用 `role="switch"`、`aria-checked` 和红/绿色视觉状态；红色状态下点击开启只发起服务端请求，不会产生订单。
- 服务端返回未就绪原因时，控件保持红色并展示原因，例如“未连接账户”“部署侧未开放”或“网关未配置”。
- 不能把“总开关关闭”解释为“既有止损关闭”；页面需明确提示既有保护仍持续执行。
- 连接状态或部署侧门槛变化时，页面刷新/轮询后必须以服务端返回值覆盖本地状态，不使用 `localStorage` 作为权威来源。

## 测试与验收

- 单元测试覆盖每个门槛、开启失败、成功开启、关闭后既有保护继续的状态语义。
- API 测试覆盖未认证、无变更权限、未连接账户、环境变量关闭和成功切换；验证服务端不接受前端伪造的“可下单”字段。
- 页面源码/渲染测试确认只有一个总开关，具备可访问性属性，不再出现相互矛盾的旧开关文案。
- 交易动作测试确认总开关关闭时新入场被拒绝，保护性动作仍可执行。
- 不使用真实交易所下单作为测试手段。
