# VPS 实盘条件执行与 Bark 通知设计

日期：2026-08-26

## 目标与边界

将交易议会部署到一台固定公网 IPv4 的 Ubuntu VPS，使用户可通过任意电脑或 iPad 的 HTTPS 浏览器登录。用户手动根据 AI 的建议创建即时订单或条件单；AI、雷达、专家会诊和策略程序均不得自行武装、创建或发送真实订单。

条件单必须在 VPS 持久化：用户设备、浏览器或网页关闭后仍持续等待，直至成交、取消或用户为该条件设置的到期时间。价格条件、止盈和止损优先交由 Binance USDⓈ-M 原生条件订单处理；均线条件和横向关键位失效由 VPS 的常驻执行器只依据已收盘 K 线判断。

本阶段不强制限制合约范围、逐仓、杠杆、单笔风险或日损失。系统展示风险建议和异常警告，但只强制执行交易所自身的精度、最小名义金额、账户权限、IP 白名单、重复请求防护和同一订单的幂等性校验。

## 非目标

- 不实现 AI、雷达或策略自动开仓。
- 不开放提现、转账或资产划转接口。
- 不把 Binance、Bark、模型或部署密钥返回给浏览器、记录到日志或提交到 Git。
- 不在开发、测试或 VPS 部署过程中发送真实 Binance 订单；生产真实操作只能由用户在已登录网站中主动提交，且执行前必须单独确认。

## 运行拓扑

```text
任意电脑/iPad
  -> 域名 + HTTPS + Caddy
  -> Trade Workbench (127.0.0.1:3000)
       -> Binance Gateway (127.0.0.1:8788)
       -> SQLite / 条件单与事件记录 (/var/lib/trade-workbench)
       -> Live Executor (systemd 常驻服务)
  -> Binance USDⓈ-M Futures
       <- VPS 固定公网 IPv4（API 白名单）
  -> Bark（仅推送）
```

仅 Caddy 对外监听 80/443。网站、网关和执行器都使用系统服务账户，Binance 网关只监听 `127.0.0.1:8788`；3000、8788 与执行器健康端口不得暴露到公网。

## 身份与开关语义

### 远程登录

新增统一的管理员登录门禁。用户输入 `OPERATOR_ACCESS_TOKEN` 后，由现有 `/api/advisory/session` 写入 `HttpOnly; Secure; SameSite=Strict` 会话 Cookie。令牌不写入 Local Storage、Session Storage、URL、应用数据库或日志。所有读取账户、创建/取消条件单、Bark 设置和实盘操作继续要求该会话。

### 即时实盘开关

设置页保留“新建即时实盘订单”开关。它默认关闭，只影响新的即时市价/限价订单，不取消、不暂停、不修改已经武装的条件单。开关状态及操作人、时间写入审计日志。

### 条件单独立武装

每条条件单单独选择执行模式：

- `PAPER`：只模拟和通知，永不发送 Binance 请求。
- `LIVE_ARMED`：用户明确确认后由 VPS 持续执行；之后即时实盘开关变化不影响它。

条件单状态机为：`DRAFT -> WAITING -> TRIGGERING -> SUBMITTED -> FILLED | REJECTED | CANCELED | EXPIRED`。撤销是唯一会停止等待的用户操作；撤销时会同时取消项目创建且仍处于 Binance 挂单状态的原生订单。

## 条件类型与执行策略

| 类型 | 判定和执行位置 | 断网/重启行为 |
| --- | --- | --- |
| 价格入场、止盈、止损、追踪止损 | Binance 原生 USDⓈ-M 条件订单 | 下单成功后由交易所持续等待；VPS 重启不影响已提交订单 |
| 均线触碰、收盘上破/下破 | VPS 执行器，按指定周期的已收盘 K 线计算 | 条件记录持久化；启动时补读遗漏的已收盘 K 线，避免因重启丢失信号 |
| 即时市价/限价 | 用户已登录、显式提交且即时订单开关开启 | 提交前产生唯一 client order ID；网络重试先查询该 ID，避免重复订单 |

对于均线条件，用户必须指定币种、周期、均线类型、均线周期数、ATR 周期、ATR 倍数、触发方向、下单参数、有效期及 `LIVE_ARMED` 或 `PAPER` 模式。均线类型首版支持 `SMA` 和 `EMA`；均线周期、ATR 周期及 ATR 倍数均由用户填写，执行器仅在可取得足够已收盘 K 线时武装条件。常见配置如 SMA30、EMA60、EMA90、SMA200，以及 0.5 ATR、1 ATR、1.5 ATR 都不需要专门编码。

### 移动限价入场、期限与成交腿

均线入场首版只发送限价单，并优先使用 Binance 的 `GTX`（Post Only）时间有效方式；如果价格会立即吃单，订单应被拒绝或继续等待，系统不得把它自动改成市价单。策略默认有效期为创建后 7 天。到期时仅撤销尚未成交的入场腿，并发送 Bark 通知；已成交部分继续由其原有止损、止盈与守卫管理。

一组均线入场可有任意数量的腿，默认三腿且按总投入金额均分，但用户可逐腿改金额。每根指定周期的**已收盘**新 K 线到来时，执行器只对完全未成交的腿重新计算 MA/ATR 价格带。计算值经交易所 tick size、step size 取整后，价格和数量未变化则不发请求；发生变化时优先修改现有订单。部分成交的腿永远保留原价、原订单和剩余数量，不会因后续 K 线而撤销或移动。每次刷新均保存网站订单号、Binance 订单号、修订号、使用的闭合 K 线与计算价格，且刷新前必须先对账，以免网络超时或重启产生重复订单。

止盈或止损的**部分**减仓不撤销其余入场腿。只有该策略已经实际成交的仓位全部被平掉（最终止盈、守卫全平或用户手动全平，且退出订单已确认完全成交）时，执行器才撤销同组仍未成交的入场腿。最终退出订单若仅部分成交，则未成交入场腿继续挂到原定 7 天期限或用户取消为止。

每个策略可附加一个或多个“失效守卫（invalidation guard）”，并明确各自的确认次数和减仓目标：

- **动态均线守卫**：多头使用 `当前 MA - ATR 倍数 × 当前 ATR`，空头使用 `当前 MA + ATR 倍数 × 当前 ATR`。例如 1H EMA30、ATR(14)、1 ATR 的多头，第一根已收盘 1H K 线收在动态线下方时将策略仓位目标降至 50%；下一根仍在动态线下方则目标降至 0%。空头规则方向相反：收在动态线上方才触发。
- **横向关键位守卫**：用户指定固定价格和方向，例如多头“已收盘 K 线跌破某支撑价”或空头“已收盘 K 线上破某阻力价”。它可使用同样的两根 K 线 50%/全部退出规则，也可以由用户选择一次性退出全部仓位。

多条守卫同时满足时，执行器计算每条守卫要求的“该策略目标剩余仓位比例”，只执行保护性最强的一项（最低剩余比例）。因此两条均要求剩余 50% 的规则不会在同一根 K 线意外叠加成只剩 25%；若横向关键位设为一次性全部退出，则它优先令该策略目标剩余仓位为 0%。第一阶段减仓后，若 K 线重新收回守卫的安全一侧，该守卫的第二阶段确认计数重置，剩余仓位继续等待新的确认。

### 毛利润分段止盈

止盈按“实际成交批次”独立管理，而不是把后续新成交的仓位倒灌进已完成批次。每个新增实际成交仓位都创建一个成交批次，记录所属网站订单号、成交均价、实际成交金额、数量、已实现利润、未实现利润和两个止盈阶段；它不混入同币种的其他策略，也不扣除手续费或资金费。入场腿可以部分成交；每个新增加的实际成交数量形成一个新批次，因而不会改变旧批次已经完成的止盈进度。

- 某批次的已实现利润加未实现利润达到该批次实际成交金额的 100% 时，预先挂出或执行第一档 `reduceOnly` 限价单，卖出/买回该批次初始数量的 25%。
- 某批次的上述累计毛利润达到该批次实际成交金额的 200% 时，预先挂出或执行第二档 `reduceOnly` 限价单，卖出/买回该批次初始数量的 40%。
- 该批次余下初始数量的 35% 不设固定止盈，继续按照策略组的动态均线守卫与可选横向支撑/阻力守卫退出。

所有止盈都优先预先挂在盘口，以限价方式成交；不得为了“立即止盈”而自动转换为市价单。第一档或第二档止盈成交后，未成交入场腿继续有效；只有策略组全部成交批次的仓位均已退出后，才按上一节撤销这些未成交腿。

策略的每笔入场都会获得网站内部订单号，例如 `TW-2340`、`TW-2341` 和 `TW-2342`，并分别保存实际 Binance 订单号、来源策略、周期、均线与 ATR 参数、入场带（例如 `MA + 1 ATR`、`MA`、`MA - 1 ATR`）、数量和成交结果。动态失效守卫属于该策略总体仓位而非单一 Binance 汇总仓位；同一币种同时运行 1H 与 4H 策略时，执行器按策略腿的数量分配 `reduceOnly` 减仓，避免把一个策略的退出计入另一个策略。

执行器只处理用户已经武装的记录；AI 建议可以预填表单和读取这些结构化订单归属以解释策略状态，但不能改写武装状态或发送订单。

所有实际请求在发送前读取最新 `exchangeInfo` 过滤器，并验证 tick size、step size、最小名义金额及 Binance 支持的订单类型。Binance 当前将 `STOP`、`STOP_MARKET`、`TAKE_PROFIT`、`TAKE_PROFIT_MARKET` 与 `TRAILING_STOP_MARKET` 定义为 USDⓈ-M 条件订单；实现应以发布时的官方接口文档为准。

## 服务端组件

### Binance Gateway

保留网关的回环监听和 Bearer token。默认 `BINANCE_GATEWAY_TRADING=false`；当用户完成生产配置后，只有网关服务端环境变量才可将其设为 `true`。网关新增精确允许列表，而不是通配的交易路径：下单、查询、撤销与项目所需的原生条件订单路径逐条允许；提现、转账、保证金划转及未列出的变更类接口始终拒绝。

网关日志只写请求类别、状态和耗时，不写 API key、签名、token、订单金额或完整参数。

### Live Executor

新增 `trade-workbench-executor.service`，以 systemd `Restart=on-failure` 常驻。它读取同一 root-owned 环境文件、条件单数据库和回环网关：

1. 在每根指定周期 K 线收盘后计算用户已武装均线条件。
2. 使用数据库租约把一条记录从 `WAITING` 原子转为 `TRIGGERING`，确保多次重启或并发不会重复执行。
3. 生成稳定的 Binance client order ID，发送或查询订单后持久化交易所订单 ID、响应摘要和状态。
4. 定期对 `SUBMITTED` 订单进行状态对账，并写入成交、拒绝、撤销和保护单状态。
5. 服务启动时回补上次成功处理之后的闭合 K 线；无法确定闭合状态时维持 `WAITING` 并记录可见诊断，而不推测成交。

### 持久化与审计

现有模拟 `conditional_orders` 保持兼容。新增实盘条件、原生订单映射、执行租约、事件和审计表；每条记录包含创建人会话摘要、创建/武装/撤销时间、模式、条件定义、有效期、client order ID、Binance order ID 与状态。不得存入 API 密钥或 session token。

## Bark 通知

新增受管理员会话保护的 Bark 设置卡：输入设备 key，显示是否已配置，支持发送测试通知和清除配置。生产环境不复用当前仅供本地开发的 D1 凭据写入路径；Bark key 存入 VPS 上仅服务账户可读的 0600 运行时密钥文件，且 API 永远只返回“已配置/未配置”的状态。

通知事件包括：条件武装、条件触发、订单受理/拒绝/成交、止盈、止损、撤销、到期、执行器不可用与恢复。每个事件有稳定 idempotency key；先持久化事件，再异步推送，失败会重试且绝不阻塞订单状态写入。

## UI 与 API

- 根布局加管理员登录门禁。
- 设置页增加即时实盘开关、Bark 配置与测试、执行器健康状态和 Binance 网关状态。
- 交易页区分模拟条件单与实盘已武装条件单，明确展示触发类型、执行模式、有效期、交易所订单号摘要、最后检查时间和撤销按钮。
- 交易页右侧由当前堆叠式选项收敛为“建立策略”递进向导：AI 摘要始终展示图表币种、评分、方向、建议入场/止损/止盈和盈亏比；向导依次选择多空、周期（默认 1H）、均线或支撑阻力策略、总投入与分腿金额、MA/EMA + 长度 + ATR 参数、可选横向守卫与最终摘要。最后一页才显示创建模拟条件单或武装实盘条件单按钮。
- 向导摘要明确展示默认 7 天有效期、未成交腿的闭合 K 线刷新规则、部分成交不移动、动态止损、毛利润 100% 时 25% / 200% 时 40% 的限价止盈及剩余 35% 跟随守卫。AI 仅能预填这些字段，不能跳过用户的最终确认。
- 新 API 只接受同源、管理员会话的请求；请求体使用明确 schema，拒绝未知字段。浏览器不直接访问 Binance 网关。
- 所有高风险动作保留一次可见的摘要确认；风险建议可由用户确认后忽略，不作为自动锁定条件。

## VPS 与上线

1. 使用域名的 A 记录指向 VPS 固定公网 IPv4，Caddy 自动签发 HTTPS。
2. `/etc/trade-workbench/workbench.env` 使用 root:root 和 0600；Binance API key 仅开 USDⓈ-M Futures 交易权限，关闭提现/转账，并将 VPS 实际出口 IPv4 加入 Binance 白名单。
3. systemd 启用网站、网关、维护定时器、执行器和健康检查；仅开放 SSH、80、443。
4. 先只读/模拟验证，再以极小资金由用户自行发起一笔生产验证订单。根据 Binance 操作规则，任何由本助手实际提交的生产交易均需用户在当次操作中明确输入 `CONFIRM`；本设计不授权代理提交订单。

## 验收与测试

- 登录门禁测试：未登录远程请求为 401；登录后得到安全 Cookie；令牌不进入浏览器持久化存储。
- 条件状态机单元测试：武装、取消、到期、服务重启、重复触发和事务租约。
- 移动限价入场测试：仅闭合 K 线刷新、完全未成交腿的重算、取整后不变不请求、部分成交腿保留原价、7 天到期仅撤未成交腿、已成交仓位完全退出后才撤剩余入场腿、最终退出部分成交时不撤入场腿。
- 毛利润止盈测试：每个实际成交批次独立作为止盈本金、已实现加未实现毛利润计算、不扣手续费/资金费、100% 时批次初始数量 25%、200% 时批次初始数量 40%、余下 35% 交给守卫，以及新成交批次绝不回填或改写旧批次已完成止盈。
- 均线回补测试：遗漏闭合 K 线会被一次处理，未闭合 K 线不触发；SMA/EMA、不同均线周期、ATR 周期与 0.5/1/1.5 等 ATR 倍数得到可复现的动态失效线。
- 失效守卫测试：多头动态线下破、空头动态线上破、横向支撑/阻力、两根 K 线的 50%/全部退出、重新收回后的确认计数重置，以及多守卫同时触发时只执行最低目标剩余仓位。
- 网关测试：默认拒绝交易；开启后只允许显式交易路径；拒绝转账/提现；所有监听仍为回环。
- Bark 测试：密钥不返回、测试消息、失败重试与去重。
- 端到端模拟：Fake Binance 网关验证唯一 client order ID、下单/撤销对账和事件顺序。
- VPS 验收：HTTPS、UFW、systemd 自动恢复、重启后的条件恢复、网关实际出口 IP、Bark 测试通知。

## 已知约束

- 均线条件由 VPS 执行器判断，因此依赖 VPS 和 Binance 数据可达；仅原生条件订单可在 VPS 暂时不可用时继续由交易所等待。
- Caddy 的可信 HTTPS 证书需要域名；裸 IP 只可用于部署期健康检查，不得用于登录或实盘操作。
- 实盘功能上线不等于允许 AI 自主交易，也不等于系统承担风险控制决策。
